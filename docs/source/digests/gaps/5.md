## 1. Verdict: it is a gap

1. The spec makes the conformance suite the proof of every client and of the gateway:
   - "AP-001. Every Atlas client, in every language, passes the conformance suite at every level it declares." (PROT:92)
   - "AP-002. The Atlas Gateway passes the gateway conformance suite." (PROT:93)
   - "A client conforms at a level when it passes every vector and every scenario of that level and of every level it requires ... with no case skipped." (98:140)
   - "No client or the gateway is released without passing the suite at its declared levels." (98:155)
2. PLAN built it in Phase 9: "`sdk/go/conformance` (the 15 capabilities, scripted scenarios, request recording, the loopback control API); all 50 scenarios; runners for Go, the CLI and Python; the gateway suite with the reference runner against the real local root" (PLAN:132).
3. PLAN's phases are gone: "The phases below are replaced by REVIEW.md's order of work." (PLAN:9). REVIEW.md's order (REV:27-33) has five steps, and none names the conformance gateway, the suite, the runners or the gateway suite. REV:21 keeps "the references as the independent check (D22)", but nothing builds the machine that runs the scenarios.
4. Nothing in the tree runs a scenario. `sdk/go/conformance` does not exist (`ls`, 22:25). The references' `check` proves only the scenarios' structure: "Exactly §9.8.4's 50 ids, each with its level, one expected result per command, known ops and assertions, and only exact-ids the fixtures serve" (RD:206). `tools/spec/atlasref/conformance.py` writes the fixtures (RD:47) and serves nothing (no server in it, grep). **No scenario has ever been executed against anything.**
5. The live acceptance harness does not stand in for it (section 6.2): it compares results, not request records, and it never produces an incomplete stream, an idempotent retry or a source failure.

So the gap is real. Sections 2-5 give the build specification; section 7 proposes who builds what, and when.

### 3.3 The runners

**The protocol** (98:35-53): reads commands as JSON lines on stdin, writes one JSON line per result on stdout, "calling only the client's public interface (9.7.1)".

- Command: `{ "id": 7, "op": "call", "args": { "address": "conformance.rows@v1:fetch", "request": { "n": 3 }, "options": { "deadline_ms": 2000, "accept": ["application/x-ndjson"] } } }` (98:42). `options` sits inside `args`.
- Success: `{ "id": 7, "ok": true, "value": [...], "warnings": [], "calls": 1 }` (98:48). Failure: `{ "id": 7, "ok": false, "problem": { ... } }` (98:51). A failed result may carry `value`, the rows read before the failure (Q-RUN-6, Q:123).
- Values as JSON; Arrow results "as arrays of row records (decimals as their strings, timestamps as RFC 3339), bytes as base64" (98:53). Date-times in UTC with `Z` and exactly six fractional digits (Q-TIME-1, Q:34).
- `version`: "the runner answers its client's name, version, protocol and levels" (98:53).
- `options`: `person: true`; `confirm: "accept"` or `"decline"` (98:53). Beyond §9.8.3: `path`, `max_memory`, `replace`, `if_match`, `fields`, `set` (RD:121; Q-RUN-4, Q:121).
- Warnings: each `{ "code", "text" }` (98:53); a deprecation's `code` is `deprecated` (Q-RUN-3, Q:120).
- `call` on an `operation` delivery returns the operation document; `operation.wait` returns its result; on a `transfer` delivery `call` returns `{"content": {"base64", "metadata"}}` in memory or `{"manifest": {"files": [...]}}` on disk; the end line's usage is returned as `usage` (Q-RUN-5, Q:122; RD:121).
- `subscribe.open` names its subscription by its command's id; `subscribe.next` with a timeout answers `{"none": true}` (Q-RUN-7, Q:124). DEFERRED with events.
- "The runner adds no logic: it translates commands into calls on the client and results into lines." (98:53)

## 5. The complications

### 5.1 `conformance.thing@v1:create` while resources are deferred

- The **client** side of CORE-CALL-001 and CORE-CALL-004 needs no resource feature. The client follows the served binding (`POST /v1/resource/conformance.thing@v1:create`, GW:1567-1592, address at GW:1585) and sends an `Idempotency-Key` because the interaction's `effect` is `write` (GW:1568). The scenario's own words: "only a call whose effect is not read carries an Idempotency-Key" (SC CORE-CALL-001 L4). The expected values are `value_contains` `{"name": "conformance/things/t1", "colour": "red"}` (SC CORE-CALL-001 L85-88).
- The **conformance gateway** needs only its own in-memory thing store, which is a fixture behaviour (RD:187), not the Atlas gateway's resource family. Create must answer the envelope that `schemas.resource` requires: `name`, `metadata` (`uid`, `etag`, `generation` ≥1, `created`, `updated`, `owner`, `labels`, `deleting`), `colour`, `size` (GW:1685-1760). For CORE-CALL-004 the retry after the scripted 503 is served by default (RD:135, "anything not scripted is served by the default behaviour below").
- So "resources are deferred" (REV:72) does not block CORE-CALL-001 or CORE-CALL-004 in the **client** suite. **IN SCOPE.** It blocks them in the **gateway** suite only (5.3).

### 5.2 `conformance.evolving@v1` and R03

- The Go resolver keeps every lens operation: "`protocol/resolve` becomes the experimental resolver ATLAS-CORE §7 allows ... Its vectors still pass" (REV:90). The Go runner, the CLI (Go) and Python (the Go engine, DD:65) can therefore pass CORE-RES-001, CORE-RES-003, CORE-LOCK-001 and COL-003 against the conformance gateway as written.
- Node is "obliged only to aliases, defaults, UNKNOWN and projection" (REV:90). A Node client built to that obligation fails those four scenarios: `convert_unit`, `promote` and `drop` backward are needed (section 4.2).
- **AMBIGUOUS:**
  - (a) Node implements the whole resolver anyway, as the second implementation (D20 DD:43, D22 DD:44), tested by `REFS/vectors/resolution.json`. Every scenario passes and no case is skipped. Cost: the R03-optional operations in TypeScript.
  - (b) Node implements only R03's obligation. Those four cases fail and are reported as failing under R03 (98:140 forbids skipping). Replacement scenarios would require a documented protocol amendment and regeneration through `tools/spec` (D22); generated scenario files must not be edited by hand. AGENTS rule: "Where the spec is ambiguous, write the case down; don't guess" (AG:7).
- Neither CD (CD:671, CD:673, CD:688 mark them DEFERRED) nor REV decides between these. CORE-RES-002 (projection only; lock and answer both #C) and CORE-DEPR-001 (no lock) need no R03-optional operation. **IN SCOPE.**

### 5.3 The gateway suite on the real gateway

The gateway suite needs the real `gateway-local` to mount `sdk/go/conformance`'s capabilities (98:136). Five things block that now:

1. **The gate refuses three fixture profiles.** The live gate refuses `drop` ("a removal is a new major version"), `convert_unit` and `promote` ("changes a unit or a type, which a version keeps ... The resolver's %s is an experiment, not a client obligation (R03)") within a version (live `classify.go:599-609`; REV:91 "`protocol/gate` takes the smaller compatibility model of R03"). So `conformance.evolving@v1` #B and #C cannot be admitted through registration. **AMBIGUOUS:** (a) the conformance profiles are mounted as fixtures that bypass the gate in `local` only; (b) the gateway suite runs without the evolving scenarios, reported as failing under R03.
2. **Resources.** The gateway suite's CORE-CALL-001/004 and CORE-ENV-001 need a resource-family service with idempotency (R08, step 3) and ETags (R14, "Resources (after the journey)", REV:72). DEFERRED with resources, unless `sdk/go/conformance`'s in-memory thing is mounted as is.
3. **R06.** The real gateway may not accept `Atlas-Confirm` as consent (REV:18), so `conformance.costly` on the real gateway waits for R06's design (step 3).
4. **The layer files.** Neither `gateway/layers.toml` (GLT:13-27) nor `gateway/local/layers.toml` (LLT:7-14) places `sdk/go/conformance/...` (or package `atlas`) in any layer. **MISSING:** the entry that lets `gateway/local` import it, and nothing else.
5. **One package, two hosts.** "Written once" (98:136) means `sdk/go/conformance` must expose its capabilities in a form the gateway can mount, and `sdk/go` cannot import `gateway/ports` (AG:26; module direction). **MISSING:** the seam; no source shapes it. **PROPOSED:** plain functions over `sdk/go/protocol` types (request JSON in, an answer or a `protocol.Problem` out), wrapped by the conformance gateway's own HTTP layer and by a gateway service in `gateway/local`.

The gateway-only checks (AP-DOC-001/002, ATLAS-VERSION-005, ATLAS-ACCESS-009/010, 98:136) need none of 1-3. They can run against `gateway-local` with the journey's own capabilities and the Go runner. **PROPOSED:** run those in the first build, and record AP-002 as partial.

## 6. Historical implementation observations

### 6.1 What exists

- `sdk/go/engine/engine.go` is "the runner protocol (§9.8.3) over the Go client ... the conformance suite's runner for the Go client, and the engine under the Python SDK" (L1-7). It dispatches `connect`, `whoami`, `catalog`, `search`, `describe`, `guide`, `access`, `call`, `fetch` (L201-219). Anything else answers `invalid_request` "the engine runs no op ..." (L220).
  - **MISSING** for in-scope scenarios: `explain` (CORE-EXPLAIN-001); `operation.get`, `operation.wait`, `operation.cancel` (CORE-OP-001); `version` (98:53).
  - `callArgs.Options` reads only `deadline_ms`, `accept`, `arrow`, `idempotency_key` (L146-151). **MISSING:** `person` and `confirm` (CORE-CONFIRM-001), and `path`, `max_memory`, `if_match`, `fields`, `set` (Q-RUN-4).
  - `Answer` adds `decimals`, `profile` and `cancelled` beyond §9.8.3's members (L44-58). This is allowed for the engine's own face (98:53); the suite reads only the JSON form.
- `clients/python/fiatlas/_engine.py` speaks the runner protocol to the engine (its docstring). There is no Python runner over the face.
- `clients/node` has `src/index.ts`, `src/schema.ts`, `bin/call.ts` and `test/journey.test.ts`. There is no runner.
- `sdk/go/conformance` and `sdk/go/cmd/conformance-gateway` do not exist.
- `Makefile:21`: `check: fmt vet staticcheck test tidy`. It runs no scenario, though PLAN:32 puts "the scenarios" in `make check`. `Makefile:48-55`: `e2e`, `e2e-python` and `e2e-node` run the journey against the development gateway.

### 6.2 Why `tests/e2e/acceptance.py` does not close the gap

- **Item 2 compares results, not request records.** The case named "2. the same request record, three clients" (acceptance.py:108) calls `same(...)` (L94), which compares result rows or problem codes. Nothing records what each client sent. REV:47 and AP-CLIENT-003 (C97:199) ask for byte-identical request records under RFC 8785. Only a recording gateway (98:57; CORE-CALL-005's `jcs` assertion) can prove that.
- **The canonical form is wrong for the claim.** `canon` is `json.dumps(v, sort_keys=True, separators=(",", ":"), ensure_ascii=False, default=str)` (L44-45). That is not RFC 8785: number forms and sort order differ (sorting by UTF-16 code units, `vectors/fingerprints.json` case "UTF-16 member order", RD:65).
- **Item 5 is narrowed.** Its docstring says "5. Invalid requests, refusals and exact decimals behave the same in every client." (L11-12). REV:50 adds "incomplete streams, idempotent retries and source failures". These are what the scripted conformance gateway exists to cause (STREAM-002, COL-002, CORE-CALL-004, CORE-PROB-001, CORE-RETRY-001).
- **Sign-in is opaque.** It signs in with opaque tokens (`atlas ... login --token dev-alice`, L69). CRITIC:288 (contradiction 6) settles that the binaries use RS256 JWTs through the real verifier (`06-7:145`).
- It is still the right home for items 3, 4 and 6, which no scenario proves (section 4.3). It stages item 4 with `-exclude portfolio.holdings-dates@v1` (L59).
