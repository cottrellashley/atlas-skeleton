## 3. How each part is built

### 3.1 The I-JSON reader (§9.1.2): IN SCOPE, and `JSON.parse` is not enough

The rules (P1:22-30): UTF-8 with no BOM; "No object has two members with the same name. A receiver MUST reject a document with duplicate names (`invalid_document`)"; no unpaired surrogates and no noncharacters; numbers are binary64, and an integer member lies within `[-(2^53)+1, (2^53)-1]`; member order carries no meaning except for a canonical form; strings compare by code points, never normalised; unknown members ignored unless closed. AP-CONV-001 (P1:105): "Every client and the gateway rejects a JSON document with duplicate member names, or a number outside the I-JSON range where an integer is required."

Measured on Node v25.6.1 (`json-check.mjs`):

| Input | `JSON.parse` / `fetch` does | I-JSON needs |
|---|---|---|
| `{"a":1,"a":2}` | `{"a":2}`, silently. `Response.json()` the same | `invalid_document` |
| BOM then `{}`, as text | throws `SyntaxError` | refuse |
| BOM bytes through `Response.text()` or `Response.json()` | **BOM stripped, accepted** | refuse. Read `arrayBuffer()` and decode with `new TextDecoder('utf-8', { fatal: true, ignoreBOM: true })` (with `ignoreBOM: true` the BOM is kept, so it can be detected) |
| Invalid UTF-8 (`C3 28`) | default `TextDecoder` gives U+FFFD; `fatal: true` throws `TypeError` | refuse |
| A lone surrogate escape (backslash-u D800) | parses; `isWellFormed()` is false | refuse |
| A noncharacter escape (U+FDD0) | parses | refuse |
| `1e400` | `Infinity` | refuse (Go's `ijson` refuses "a number beyond binary64", REPO/sdk/go/protocol/ijson/ijson.go:4-5) |
| `9007199254740993` | `9007199254740992` | binary64 reading is right ("Numbers compare as binary64", README:63; V/schemas.json "maximum: 2^53+1 is read as 2^53" is *valid*). An `integer` there is outside I-JSON: `Number.isSafeInteger` is false, so `type` fails (V/schemas "type integer: 2^53 is outside I-JSON") |
| `-0` | `-0` | equals `0` (V/schemas "const: -0 equals 0") |
| `{"b":1,"10":2,"a":3,"2":4}` | key order `2,10,b,a`: integer-like keys move first | Order matters for a schema's `properties` (Arrow field order and §9.5.2's matching order, Q-ARROW-1 at Q:7; README:63). Safe only because `property-name` must start with `a-z` (P1:46), so no schema property is integer-like. A reader that keeps order (an array of entries or a `Map`) is the robust choice |
| `{"__proto__":{...}}` | own property, no pollution | Keep it so. Never `Object.assign` parsed data onto a plain object |
| A reviver's third argument | `context.source` gives the exact source text (`9007199254740993`) | Can recover a number's text if wanted. Go keeps "the exact text it was written with" (ijson.go:8) |

What the reader must do, from the rules above:
1. Decode the bytes strictly (fatal, BOM kept, and a BOM refused).
2. Parse with a hand-written recursive-descent reader that refuses duplicate names at any depth, noncharacters and unpaired surrogates (escaped or not), non-finite numbers and trailing data.
3. Keep member order.
4. Bound depth.

Go bounds depth at 128 by default (`ijson.go:217`, `MaxDepth = 128`). That is Go's choice, not the spec's. DECISION NEEDED: adopt the same limits in Node for parity, and record them.

Where it applies: every JSON document "bodies, profiles, events, test vectors" (P1:22). That includes NDJSON lines, the end line, problems, the bootstrap, describe answers, the token file and the lock (after TOML parsing).

### 3.3 RFC 8785 and fingerprints (§9.4): IN SCOPE, and Node's built-ins suffice

- The projection (P4:15-28) removes the top-level `fingerprint`, `revision`, `usage`; `identity.title`, `.summary`, `.owner`; `description` and `next` of every `errors` member; `evolution.changelog`. In every `schemas` member it applies StripSchema: removes `title`, `description`, `$comment`, `examples`; recurses into `properties`, `$defs`, `items`, an object `additionalProperties`, and `prefixItems`, `anyOf`, `oneOf`; removes `description` from `x-atlas-enum` elements and `reason` from an object `x-atlas-deprecated`. It works "only at **schema positions**": "a property *named* `title` under `properties` is kept."
- Canonical form (P4:32): "members sorted by their names' UTF-16 code units, no whitespace, strings with only the escapes RFC 8785 requires, numbers in ECMAScript's shortest form". Then UTF-8, SHA-256, 64 lowercase hex characters; "the **fingerprint** is the first 16" (P4:33-35).
- The client "recomputes it on every profile it receives and treats a mismatch as `invalid_document`" (P4:37; P7:104; CORE-DISC-001 at P8:92).
- In profiles, `errors` is an array (measured in V/fingerprints.json).
- **Measured.** A 20-line implementation reproduces the canonical text, SHA-256 and fingerprint of **all 9** cases of V/fingerprints.json (`jcs-check.mjs`). It uses `Object.keys(o).sort()` (JavaScript's default sort compares UTF-16 code units, measured: U+1F600 sorts before U+FB01), `JSON.stringify` for strings and numbers (ECMAScript's shortest form), and `createHash('sha256')`. The cases are: complete; prose-changed-and-reordered; column-added; non-ascii-quote-tab; control-characters; utf16-member-order; numbers (`1e+21, 1e-7, 0.000001, 100, -0 as 0, 5e-324`); prose-at-every-schema-position; the-same-without-that-prose. The draft's `canonical`/`fingerprint` also passes 9/9, and the `profiles/data.json` fingerprint.
- Guards: refuse non-finite numbers. Canonicalise only I-JSON input (no lone surrogates).
- For a page, `node:crypto` is not available. `crypto.subtle.digest('SHA-256', ...)` is (async).
- AP-CLIENT-003 (P7:199): the request record "is byte-for-byte the same JSON from every client (canonicalised by RFC 8785)". CORE-CALL-005 (REFS/scenarios/CORE-CALL-005.json) asserts `jcs` = `{"count":2,"kind":"loud","ratio":0.5,"tags":["b","a"],"text":"naïve é","when":"2026-10-31"}` for the input `{text, count, ratio, when, kind, tags}`. README:157 defines `body` ... `jcs`.

### 3.5 The Atlas Schema validator (§9.2): IN SCOPE; written by hand is the natural reading

**The rules a validator implements:**

- The result: "`valid`, or every failure, each with the instance's JSON Pointer (RFC 6901) and the keyword that failed. The problem for an invalid request is `invalid_request`, with each failure in `details` and the first one's pointer as `target`" (P2:99).
- The order (Q-VAL-1 at Q:13; A-009): "sort by pointer, then by keyword, comparing code points, and give each pair once. So `/10` sorts before `/2`". `required` reports at the missing member; `additionalProperties: false` and `items: false` at the extra one; `anyOf`/`oneOf` give one failure, at the instance; a logical type reports under the keyword it expands to (Q:139).
- `details` items: `{code, target, keyword}` per failure (Q-DOC-9 at Q:64).
- A client "MUST validate every request against its schema before sending it" (P2:141). CORE-CALL-002: "An invalid request fails `invalid_request` with its pointer, and nothing is sent" (P8:97). AP-SCHEMA-001 (P2:150).
- UNKNOWN (P2:65; Q-DOC-1 at Q:10; README:55): a result enum includes `UNKNOWN`. "A client maps a value it does not know to it before validating."

**JavaScript pitfalls, each shown by a vector or a measurement:**

| Pitfall | Do this | Evidence |
|---|---|---|
| `string.length` counts UTF-16 units | Count code points (`[...s].length`) | V/schemas "minLength counts code points: U+1F600 is one"; measured `2 vs 1` |
| Default sort and `<` compare UTF-16 units | Q-VAL-1 needs **code points**; RFC 8785 needs **UTF-16 units**. Use two comparators. They differ only between astral characters and U+E000-U+FFFF | Q:13; P4:32; V/fingerprints "utf16-member-order" |
| `Number.isInteger` accepts 2^53 and 1e300 | `integer` = `Number.isSafeInteger` | V/schemas "2^53 is outside I-JSON", "1e300 is outside I-JSON" |
| Stopping at the first failure per schema | Evaluate every keyword: `{"z":5.5}` against `{type: integer, minimum: 10}` gives **both** `/z minimum` and `/z type` | V/schemas "many failures, sorted by pointer then keyword" |
| Equality for `enum`/`const`/`uniqueItems` | Numbers as binary64 (`1.0 == 1`, `0.10000000000000000001` equals `0.1`), objects regardless of member order, `"1" != 1`, `true != 1` | V/schemas enum/const/uniqueItems cases |
| Passing `pattern` straight to `new RegExp(p, 'u')` | Translate the I-Regexp (below). `$` inside *R* is a character | V/schemas "pattern: $ inside R is a character" |
| JavaScript `.` does not match `\n`, `\r`, **U+2028, U+2029** | RFC 9485 §5.3 replaces each unescaped `.` outside a character class with `[^\n\r]` | RFC 9485 §5.3 (fetched); V/schemas ". does not match LF/CR", ". matches one code point" |

**I-Regexp to ECMAScript.** Every `pattern` is `^ R $` with *R* an I-Regexp (RFC 9485), matched against the whole value's code points, case-sensitive. "A validator translates *R* to its own engine as RFC 9485's section 5 describes" (P2:91). RFC 9485 §5.3, read from rfc-editor.org:
1. "For any unescaped dots (.) outside character classes ... replace the dot with [^\n\r]."
2. Wrap the result in `^(?:` and `)$`.
3. Interpret it "as a Unicode pattern" (`u` flag).

So strip the Atlas `^`/`$`, translate *R*, and wrap it. Q-RE-1 (Q:12; A-013) adds: refuse `\p{C}` and `\p{Cn}`, and counts above 1000. I-Regexp has no `\d`, `\w`, `\s`, backreferences or lookahead (RFC 9485 §1, §5.1). V/schemas has "profile" cases refusing `\d`, a lookahead, a backreference, an unescaped `{`, a count above 1000, and `\p{Cn}`.

AMBIGUOUS: whether Node needs the 71 `kind: profile` cases (the gate's rules). (a) No: Q-DOC-3 (Q:58) says "A 1.0 client reading a profile that uses a 1.1 logical type must not refuse it. The gate checks the meta-schema", and §9.2 Rule 1 puts the refusal on "the gate and registration" (P2:140). (b) Yes: P8:140 says a client passes "every vector ... with no case skipped". Under (a), Node still needs an I-Regexp check, to decide what to do with a pattern it cannot translate. DECISION NEEDED.

**Why no stock validator.** These requirements come from the sources: Q-VAL-1's (pointer, keyword) sort; `required` at the missing member's pointer; one failure per `anyOf`/`oneOf`; logical types reported under their expanded keyword; I-Regexp translation; binary64 integers; the Atlas formats. The reference itself had to extend `jsonschema` "with the profile's I-Regexp, formats, logical types and binary64 integers" to act as a second evaluator (README:200). A hand-written validator over the ~30 keywords is the natural reading. The draft's `schema.ts` is one (152 lines).

### 3.8 NDJSON and the end line (§9.6.5): IN SCOPE

- "One JSON record per line ... each line ended by a single `LF`, no blank lines. The **last** line is the end line (`chunk-end.schema.json`): `{ "$atlas": "end", "rows", "truncated", "usage", "problem" }`. A failure after the first row is reported in the end line's `problem` ... A body that ends without an end line is incomplete: the client treats it as the problem `upstream_failed`" (P6:79).
- Rule 3: "An answer without an end line or final batch is never treated as complete" (P6:101). AP-HTTP-002 (P6:110). AC:206: "EOF alone is not success."
- `chunk-end.schema.json`: required `$atlas` (`const: "end"`), `rows` (integer ≥ 0, "Rows sent"), `truncated` (boolean), `usage` (object), `problem` (`null` or a `$ref` to `problem.schema.json`) (REFS/schemas/chunk-end.schema.json:7-41).
- Q-DOC-15 (Q:70): `truncated: true` with `output_limit_exceeded` (status 200) is a **warning**; any other problem is raised after the rows. STREAM-001: all rows, then usage (P8:118). STREAM-002: no end line → `upstream_failed` (P8:119). STREAM-003: a problem after rows is raised after the rows (P8:120). STREAM-004: warning `output_limit_exceeded`, rows returned (P8:121).
- Q-RUN-6 (Q:123): a failed result may carry `value`, the rows read before the failure. STREAM-003's expected result is `ok: false` with `problem.code` `internal` and `value` the two rows.

How, in Node:
- Iterate `res.body` (async iterable of `Uint8Array`).
- Decode with a streaming `TextDecoder('utf-8', {fatal: true, ignoreBOM: true})`.
- Split on LF only, refusing blank lines.
- Parse each line with the I-JSON reader of §3.1.
- Treat a line with `$atlas` as the end line (row properties start `a-z`, P1:46). Data after it is an error.
- Treat EOF without the end line as `upstream_failed`.
- Yield rows lazily (AC:138).

For parity with Go:
- A last line without its LF is "its last line is cut short", which is incomplete (REPO/sdk/go/protocol/frame/frame.go:306-309).
- A line longer than `MaxLine = 16 << 20` (frame.go:43) is invalid.
- Both are Go's choices, not the spec's: DECISION NEEDED to adopt them.

AMBIGUOUS: STREAM-003's script writes the end line's `problem` as `{"code": "internal", "retryable": false}`, which is not a full problem document. Readings: (a) the conformance gateway fills `type`, `status` and the rest, as README:144 says it does for `respond.problem`; (b) it sends the line verbatim, and a client that validates the end line against `problem.schema.json` would refuse it.
