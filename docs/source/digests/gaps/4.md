## 0. Verdict: the gap is real

1. **The spec makes `DataSource` the one engine port.** Five places say so:
   - §6.4 rule 1: "Services reach engines only through the `DataSource` port" (`SPEC/06-4-data-sources.md:52`).
   - D28: "Engines are reached through one `DataSource` port" (`SPEC/08-design-decisions.md:50`).
   - §6.5.3 lists `DataSource (§6.4)` among the infrastructure ports in `ports` (`SPEC/06-5-packages.md:103`).
   - §6.5.12 gives it its own module namespace: `datasource` → `datasource.snowflake`, `datasource.duckdb` (tests) (`06-5:207`).
   - PLAN.md §4 names the port `DataSource` and calls `Warehouse` an "adapter-internal `Warehouse` seam" (`REPO/docs/pass-2/PLAN.md:84`).
2. **The review does not change this.** No R row in REVIEW.md amends §6.4 or PLAN §4 (`REPO/docs/pass-2/REVIEW.md:57-84`). REVIEW.md:5 governs PLAN only where the two disagree. CRITIC.md:293 reaches the same conclusion: "No decision in REVIEW.md, so PLAN governs unless a departure is recorded". `REPO/docs/pass-2/ASSUMPTIONS.md` records no departure: its rows end at A-030, `gate.Lint` (L40).
3. **The live tree inverts the layering.**
   - `ports.Warehouse` is the port. It takes a declarative `Query` and returns `Rows` of `[]any` (`REPO/gateway/ports/warehouse.go:12-30, 89-102`).
   - `views.Provider` is the only provider, and it calls the warehouse port directly (`REPO/gateway/views/views.go:137-140, 305`).
   - Nothing in the tree carries a plan, an estimate, a query id, a settle step, engine capabilities, health or a tag that reaches the engine (§4 below).
4. **The parts the tree does have are sound, and they are the inner seam.**
   - The declarative query has no SQL text, and every value is a parameter (warehouse.go:8-11).
   - The compiler runs sqlglot and the guard (`REPO/gateway/adapter/snowflake/compile.go:155-258`).
   - The `porttest.Warehouse` suite runs both the Go fake and DuckDB (`REPO/gateway/porttest/warehouse.go:68-185`; `REPO/gateway/fakes/fakes_test.go:14`; `REPO/gateway/local/duckwh/duckwh.go:24-38`).
   - INTEGRATIONS says the compiler interface takes "the capability's approved model, request, scope and schema metadata" (`SPEC/review/INTEGRATIONS.md:60`). The `Query` is close to that input.

   So the fix is to put `DataSource` above this seam. Nothing here needs to be thrown away.

## 1. What the spec requires of the data port

### 1.1 The operations (§6.4.1, `SPEC/06-4-data-sources.md:59-72`, copied exactly)

"A port in `ports` (§6.5), a Go interface, implemented once per engine" (L61):

| Operation | Does | Journey |
|---|---|---|
| `capabilities()` | What the engine supports: native Arrow results, handoff (and its chunk format version), export, estimates, client execution and its driver kind | IN SCOPE (so the gateway can tell, for example, that estimates exist but handoff does not) |
| `plan(request, writer_schema)` | Renders the request as the writer contract: one statement, every column aliased to its contract name and cast to its contract type, filters and limits pushed down; checks it with the read-only guard | IN SCOPE |
| `explain(plan)` | The plan as it would run (the statement) and its estimated size, for choosing the execution | IN SCOPE (see §1.4) |
| `execute(plan, deadline)` | A stream of Arrow record batches **already in the writer schema**, with the engine's query id | IN SCOPE (the Arrow form: see AMBIGUOUS A1) |
| `handoff(plan)` | Where supported: the handoff document for the result | DEFERRED (R10; REVIEW.md:15, :68) |
| `export(plan, format, destination)` | Writes the result as files and returns their links | DEFERRED (not in the journey; REVIEW.md:33 "direct downloads" are step 5) |
| `resume(query_id, from_batch)` | Where supported: the rest of a stream, from the engine's persisted result | DEFERRED (see AMBIGUOUS A6) |
| `settle(query_id)` | Rows, bytes and cost, from the engine's own record | IN SCOPE (R09, see §1.5) |

The class diagram uses these exact signatures (06-4:21-31): `+capabilities()`, `+plan(request, writer_schema)`, `+explain(plan)`, `+execute(plan, deadline)`, `+handoff(plan)`, `+export(plan, format, destination)`, `+resume(query_id, from_batch)`, `+settle(query_id)`.

The six steps of the planned-query path (INTEGRATIONS:64-69):
1. Validate the business request and the authorised scope before planning.
2. Build a typed AST, and "Bind scalar user values through the driver; never construct SQL by string concatenation".
3. Qualify names, and walk every scope against Atlas's allowlists.
4. Generate strictly in the target dialect and validate again.
5. "Return an immutable plan containing SQL, parameter bindings, referenced objects, output contract, request identity and provenance. Both `explain` and execution use this compiler path. A byte-identical execution promise requires the same retained plan and bindings, not two independent compilations after metadata changes."
6. "Let the Snowflake adapter own driver execution, source estimates, cancellation and returned Arrow/type checks."

## 2. What the spec requires of the provider (service) boundary

### 2.1 The service protocol (§6.1.6, 06-1:165-175, copied exactly)

"between the front door and a service host; in process, the same calls are Go calls on the ports" (L165):

| Call | Purpose | Journey |
|---|---|---|
| `describe` | The service's declaration and every profile; called at registration and when the service says it changed | IN SCOPE (the tree: `registry.Entry{Profiles, Provider}`, `REPO/gateway/assemble/assemble.go:126-153`) |
| `health` | Liveness, readiness, and availability per capability (a suspended warehouse) | IN SCOPE in part (see AMBIGUOUS A5) |
| `invoke` | A single answer, with the signed token and the request | IN SCOPE (the tree: `Provider.Serve`) |
| `start`, `get`, `cancel` | An operation | DEFERRED: no journey interaction declares `operation` delivery (§4.6) |
| `stream` | A chunked answer or a subscription, with resumption | IN SCOPE for a chunked answer (holdings is `chunked`); resumption DEFERRED (A6) |
| `plan` | A handoff document, or an export's links | DEFERRED (R10) |
| `settle` | A handed-off or exported call's actual use, from the source's record | DEFERRED for handoff and export. The streamed call's settlement comes from `DataSource.settle` (§1.5) |

- §6.1.7 rule 2: "Everything crossing a port is serialisable (typed records, Arrow, bytes); no live objects, callbacks or shared handles." (06-1:184)
- **ATLAS-GATEWAY-003**: "Every service passes its conformance batteries in process and through the service protocol." (06-1:53). **OVERRIDDEN BY REVIEW: R20**: "In-process provider conformance first; remote transport conformance when a provider is first extracted" (REVIEW.md:78). ### 2.2 Where the boundaries lie (ATLAS-CORE §8)

- "The front door owns common policy. The provider owns business meaning and source work. The source adapter owns credentials, driver behavior and encoding conversions. Remote providers receive a narrowly scoped invocation credential bound to the approved request" (ATLAS-CORE.md:184).
- "Start with these boundaries in one Go deployable and a worker where durable work needs it." (ATLAS-CORE.md:186)
- "Do not implement an independent entitlement engine in every service. Do supply providers with the enforced scope they need, and retain source-level controls as an additional check." (ATLAS-CORE.md:188)
- The INTEGRATIONS path is `Invoke → Provider[Domain capability provider] → Compiler[Atlas SQL compiler and guard] → Adapter[Snowflake adapter] → Source` (INTEGRATIONS:20-30). "Keep the library's AST internal to that integration." (INTEGRATIONS:60)
- The first release "does not require arbitrary remote provider hosting, ... multiple SQL backends" (ATLAS-CORE.md:245).

These map onto the ports as follows. This is a reading; the sources do not name a port per box:

| INTEGRATIONS box | §6.4 / §6.1 name | Tree |
|---|---|---|
| Domain capability provider | a service (`invoke`, `stream`, ...) | `ports.Provider`, implemented by `views.Provider` |
| Atlas SQL compiler and guard, Snowflake adapter | `DataSource` (`plan`, `explain`, `execute`, `settle`) | absent as a port. `snowflake.Compile` and `snowflake.Warehouse` sit behind `ports.Warehouse` |
| Snowflake with constrained identity | the engine behind the adapter-internal `Warehouse` seam (PLAN.md:84) | `database/sql` with a driver (`REPO/gateway/adapter/snowflake/warehouse.go:32-50`) |

## 4. What the live tree has (read 2026-10-31, about 22:20; the tree is still changing)

### 4.1 `ports.Warehouse` (`REPO/gateway/ports/warehouse.go`)

- `Query{Object string; Columns []Column; Where []Predicate; Latest *Latest; OrderBy []string; Limit int; Tag string}` (L12-30).
  - `Object` is `database.schema.object` (L13).
  - `Limit` of 0 means no limit (L25).
  - `Tag` "names the capability the read serves, for the warehouse's own records (Snowflake's QUERY_TAG); it is never part of the statement" (L27-29).
- `ColumnType` values and their Go types (L45-53): `string` (string), `integer` (int64), `float` (float64), `decimal` (string, "the exact decimal, never a float"), `boolean` (bool), `date` (string `YYYY-MM-DD`), `timestamp` (`time.Time`, UTC). "A null is nil in every type" (L43-44).
- `Op` values: `in`, `eq`, `gte`, `lte` (L59-64).
- `Predicate{Column; Op; Type; Values []any}` (L68-73).
- `Latest{Date; Per []string; OnOrBefore string; Within []Predicate}` (L77-84).
- `Rows{Next() ([]any, error); Close() error}`: `io.EOF` after the last row, and `Close` is idempotent (L86-92).

### 4.3 The consumer, `views.Provider` (`REPO/gateway/views/views.go`)

- It holds a `ports.Warehouse` (L137-140) and serves every interaction it holds a view model for (L227-314).
- It sets `q.Tag = inv.Capability + ":" + inv.Interaction` (L243), and the exists check uses `inv.Capability + ":exists"` (L390). The tag is neither the request id nor the idempotency key. Compare 06-1:187.

## 6. Ambiguities

- **AMBIGUOUS A1: Arrow, or typed rows, across the port.** §6.4.1 says `execute` returns "A stream of Arrow record batches" (06-4:68; 00-vision:164; 06-5:113). §6.1.7 rule 2 allows "typed records, Arrow, bytes" across any port (06-1:184). R11 makes "Core ... JSON, and Arrow is an optimisation of the same meaning" (REVIEW.md:69), but R11's row is about clients and the wire ("Every table lands as Arrow; a token file in every client").
  - (a) Keep Arrow at `DataSource.execute`, as the spec says. Arrow is in `gateway/go.mod`; `gosnowflake WithArrowBatches` (4.7) avoids conversion.
  - (b) Typed rows (the tree's `[]any` with `ColumnType`), recorded as a departure justified by R11. A row-at-a-time stream still keeps memory flat (ATLAS-SNOWFLAKE-002).

  Either reading must keep exact decimals (ATLAS-SNOWFLAKE-004) and the writer schema check (06-4:53).
- **AMBIGUOUS A2: what settlement covers for a streamed, unmetered read.**
  - (a) Every executed call gets a settlement fact from `settle(query_id)`: 06-2:146 ("copied in at settlement"), 02-2-1:106 (Streamed: "Exact"), 06-1:264 (unbudgeted reads "not settled" only in degraded mode), ATLAS-CORE.md:180.
  - (b) Only handed-off, exported or brokered calls settle from the source's record (02-2:45; 06-1:245). The streamed call's facts are the gateway's own row count plus the query id.

  R07 adds budget authorities only per *metered* provider (REVIEW.md:65). Either reading needs the query id from `execute`.
- **AMBIGUOUS A3: whether the contract must be in the SQL now.**
  - (a) Yes. §6.4.1 `plan` (06-4:66), §2.2.1.5 (02-2-1:135), and explain's `statement` "every column aliased and cast" (explain.schema.json:59) all say so. The tree's Go mapping (views.go) would then only confirm it.
  - (b) It matters only once the bytes bypass the gateway (handoff, export, ticket), all DEFERRED. Streamed results are mapped and checked by the gateway (pipeline `Rows` checks rows against the schema, pipeline.go:286-291).

  Reading (a) changes what `explain` shows; reading (b) leaves explain showing source-named columns.
- **AMBIGUOUS A4: what `QUERY_TAG` holds.**
  - (a) The request id (pass 1's test expects `QUERY_TAG=req-1`, pass1 digest §1.5).
  - (b) The call's idempotency key or operation name (06-1:187; ATLAS-OPERATION-003 cancels "by its tag").
  - (c) The capability address (the tree: views.go:243).

  Whichever is chosen, the sources fix two things: the tag is out of band (CRITIQUE.md:32), and explain reports it separately as `plan.query_tag` (explain.schema.json:61-64), so the statement stays byte-identical. ATLAS-CORE §8 also correlates facts by "request, attempt and operation id" (ATLAS-CORE.md:226).
- **AMBIGUOUS A5: availability in the first build.**
  - (a) The port reports health (06-1:170 "availability per capability (a suspended warehouse)"), and a breaker in core sets `unavailable` (06-7:154; ATLAS-GATEWAY-006; the blast-radius row 06-1:298).
  - (b) Defer the breaker. Describe answers `available` (describe.go:95), and source failures surface only as the declared problem (views.go:426-431), which acceptance item 5 already covers ("source failures behave the same in every client", REVIEW.md:50).

  Neither the review nor REVIEW.md mentions the breaker.
- **AMBIGUOUS A6: resuming an incomplete stream.** `resume(query_id, from_batch)` is "Where supported" (06-4:71). ATLAS-CORE: "any resumable position tied to the same result and scope. Resuming must not silently rerun a changing query" (ATLAS-CORE.md:206). Acceptance item 5 requires only that incomplete streams "behave the same in every client" (REVIEW.md:50).
  - (a) Defer resume and report it unsupported in `capabilities()`.
  - (b) Build it on `WithFetchResultByID` (02-2-1:68).
- **AMBIGUOUS A7: "never construct SQL by string concatenation"** (INTEGRATIONS:65).
  - (a) The clause concerns user values only: "Bind scalar user values through the driver". The tree binds every value (compile.go:75-101).
  - (b) It concerns the whole statement. The tree builds the text with `fmt` from regex-checked identifiers, then parses it (compile.go:44-49, :243-277), rather than building the AST directly ("Build a typed AST", INTEGRATIONS:65; "builds each plan as one typed syntax tree", 06-4:83).
- **AMBIGUOUS A8: the service port's name and shape.** §6.5.3 names a service port `Adapter` (06-5:103, :206), defined nowhere. The provider protocol is open (00-vision:188). The tree's `ports.Provider` stands in for it. Readings:
  - (a) `Provider` is the `Adapter` service port, under another name.
  - (b) `Adapter` is something else, still to be defined.

  Record the name.
- **AMBIGUOUS A9: where `DataSource` sits relative to the provider.** §6.4 rule 1 says "Services reach engines only through the `DataSource` port". INTEGRATIONS puts the "Atlas SQL compiler and guard" between Provider and Adapter (INTEGRATIONS:24-27).
  - (a) `views.Provider` (the service) holds a `ports.DataSource`; the compiler and guard live in `adapter/snowflake` behind `plan`.
  - (b) The compiler is its own Atlas-owned package between them.

  §6.5.3 puts "planning through the Go SQL library, the read-only guard" in `adapter/snowflake` (06-5:113), which favours (a).
