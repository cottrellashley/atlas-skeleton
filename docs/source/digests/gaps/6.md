## 0. Verdict

**The gap is real.** No digest read the driver. The digests only repeat the spec's names: gateway-access.md L439, journey.md L162-165 and L191, and gateway-front.md L561. The driver also has five properties no source mentions, and step 5 has to deal with each:
1. A **cgo file** that is built by default (`minicore_posix.go`, `import "C"`, build tag `!windows && !minicore_disabled`; GSF/minicore_posix.go L1-33). An `init` also starts a goroutine that **writes an embedded native library to disk and `dlopen`s it** (GSF/minicore.go L164-205, L296-337).
2. With **async mode, a deadline or a cancel sends no abort to Snowflake** (GSF/async.go L36-46, L141-203). The automatic abort exists only for synchronous queries (GSF/restful.go L204-212).
3. **No exported API cancels by query id or by tag.** The abort uses the driver's request id, and is unexported (GSF/restful.go L447-522).
4. `QUERY_TAG` is a **per-statement request parameter** (`WithQueryTag`), so it never appears in the SQL text (GSF/connection.go L129-131). This settles CRITIQUE #13.
5. In Arrow batches, **`WithHigherPrecision` leaves each NUMBER column exactly as Snowflake sent it**: a scaled integer (Int8 to Int64) or a Decimal128, with no scale applied. Without it, every scaled NUMBER becomes **Float64** (GSF/converter.go L3048-3089, L3280-3298).

Reader's notes:
- With higher precision, a `NUMBER(p,s)` batch may be Int8, Int16, Int32, Int64 or Decimal128 from one batch to the next. The adapter's cast to the writer's `Decimal128(p,s)` must accept every one of them, scaled by the row type's `scale`.
- The driver takes the scale from the JSON row type (`execResponseRowType.Scale`, GSF/query.go L49-58), not from Arrow metadata. The Arrow field-metadata key names are not in the driver: AMBIGUOUS, the same assumption as Q-SNOW-1 (`logicalType` `FIXED`).
- `scale` is reachable from `driver.Rows` through `ColumnTypePrecisionScale(index) (precision, scale int64, ok bool)`, for `fixed`; `time` and `timestamp` return their scale as precision (GSF/rows.go L119-136).
- `ColumnTypeDatabaseTypeName` returns the upper-cased Snowflake type (`FIXED`, `TIMESTAMP_NTZ`, ...) (rows.go L86-92).
- With `UseMicrosecondTimestamp`, NTZ and TZ come with no `TimeZone`. The writer type is `timestamp[us, tz=UTC]` (code-api.md L285). So the adapter relabels the type, which is zero-copy for TZ and LTZ. NTZ is correct only after "converted to UTC in the SQL" (§2.2.1.6 L148).
- Snowflake's own behaviour behind these conversions (CONVERT_TIMEZONE's return types, for instance) is in no source read here. That is the spike's question (§2.2.1.8 L164).

Such code keeps the licence and is listed in the module's `THIRD_PARTY_NOTICES.md`. Today that file exists only at REPO/sdk/go/THIRD_PARTY_NOTICES.md, with a "shared gateway patterns" section (L1-9).
- The driver has no NOTICE file, so Apache-2.0 §4(d) adds nothing (GSF/LICENSE L106-121 is the clause).
- AMBIGUOUS: whether a linked, non-adapted dependency must still be listed somewhere. AGENTS.md and PLAN.md say nothing.

## 5. Ambiguities, gaps and conflicts

- **A1, the gateway's Snowflake credential.** 06-3 L88 says "The gateway's service identity"; L125 gives the scope `api://<Snowflake's app>/SESSION:ROLE-ANY`; PLAN.md L84 lists "read-only role, OBO scope". The driver offers `OAUTH` + `Token` (or `TokenFilePath`, re-read at each login), `WORKLOAD_IDENTITY` with `workloadIdentityProvider=AZURE` (+ `workloadIdentityEntraResource`), `SNOWFLAKE_JWT` (key pair), `PROGRAMMATIC_ACCESS_TOKEN` and `OAUTH_CLIENT_CREDENTIALS` (§3.4). Readings:
  - (a) An Entra token for Snowflake's app through `OAUTH`, with a `driver.Connector` that puts a fresh token into each `Connect`. `Connector.Connect` copies `cfg` each time (connector.go L26-34).
  - (b) `WORKLOAD_IDENTITY` / `AZURE`.
  - (c) A key pair from Key Vault.

  No source chooses. Whatever is chosen, `Role` = the read-only role (06-4 L84), never `SESSION:ROLE-ANY`'s "every role of its identity" (06-3 L88).
- **A2, where the driver import lives.** SPEC/06-5 L113 puts `gosnowflake` in `adapter/snowflake`. REPO/gateway/layers.toml L54-57 forbids any third-party import in `gateway/adapter/...` and plans `database/sql` registration (drivers.go L3-15). But Arrow batches, `WithQueryTag` and the rest need the driver's symbols (§3.5-3.6), and `database/sql` alone cannot reach them. Readings:
  - (a) Follow the spec: `adapter/snowflake` imports gosnowflake and arrow-go, with a `[[external]]` entry for it. Then the local root (local/layers.toml L5 imports adapters) links the driver too.
  - (b) A separate package that only `cmd/gateway` imports holds the gosnowflake calls behind an adapter-internal seam, so the DuckDB path stays driver-free. This is the critic's "only `cmd/gateway` imports it" (CRITIC.md L160).
  - (c) `cmd/gateway` as its own module, like `gateway/local`, so `gateway/go.mod` never requires the driver.

  The spec wins over the live file (AGENTS.md L7), but the spec does not say which package within the adapter.
- **A3, a statement timeout from the remaining deadline.** No source names one (CRITIC.md L157). The driver gives:
  - (a) The context deadline. In sync mode it aborts by request id on expiry (restful.go L204-212). In async mode it does not (async.go L57-79).
  - (b) A session parameter at login. It applies to every statement of the session, not per statement.
  - (c) `ALTER SESSION` before each statement. That is an extra statement which the read-only guard (06-4 L84; guard reason `ddl`/`not_a_query`, code-api.md L542) would refuse, so it would have to bypass the guard.

  Reader's note: (a) in sync mode is the only per-call bound the driver honours without new statements.
- **A4, sync or async.** §2.2.1.4 L126 and PLAN.md L84 require `WithAsyncMode`. But async mode loses the automatic abort on deadline and disconnect (§3.9, §3.12), which INTEGRATIONS L96 and R17 (REVIEW.md L75) need. Readings:
  - (a) Async always, plus an explicit cancel (A5).
  - (b) Sync on the request path (`WithQueryIDChan` for the id), and async only for operation work in the worker. Constitution rule 12: "Anything slower than its deadline is an operation" (AGENTS.md L30).
- **A5, cancel by tag (ATLAS-OPERATION-003, 06-1 L67; 06-7 L187).** The driver has no exported cancel by id or by tag (§3.12). Its abort needs the original request id, in the same process. A taken-over operation runs in another replica. Readings:
  - (a) A SQL cancel, Snowflake's system function by query id, after finding the ids by tag in query history. Neither the function nor the history view is in any source read here, and the guard refuses `system_function` (code-api.md L542).
  - (b) Set a deterministic `WithRequestID` (util.go L65-68) so that a successor can abort. But `FuncCancelQuery` is unexported.
  - (c) Rely on session logout (`KeepSessionAlive` false, doc.go L1370) and `ABORT_DETACHED_QUERY` (doc.go L1374).

  Is it in scope? The first journey's capabilities are reads. AMBIGUOUS whether any of them runs as an operation, so OPERATION-003 may not bind the first build.
- **A6, what goes in the tag.** Live: `capability:interaction` (views.go L243, L390), the same for every call. The spec: the tag is how a source's record is matched to a call for settlement (02-2 L45), cancellation (06-1 L67) and "checked before a statement is run again" (06-1 L187), and the call's idempotency key or operation name travels in it. Readings:
  - (a) The tag includes the request id or operation name, so it is unique per call.
  - (b) It stays per capability, and settlement uses the query id instead.

  R09's settlement fact (REVIEW.md L67) needs per-call matching. The tag must never carry a token or key (MECH-014, AGENTS.md L47). AMBIGUOUS whether an idempotency key counts as a "key" there.
- **A7, resume from batch k.** §2.2.1.4 L130. The driver re-fetches a result by query id (§3.13), but nothing in it promises the same batch boundaries on a re-fetch. In Arrow-batch mode the first batch exists only when the inline rowset decoded (chunk_downloader.go L254-259, L290-308). So "batch k" in the original and in the re-fetch may differ. Resume is listed with handoff in §6.4.1 L71 ("Where supported"). Readings:
  - (a) DEFERRED with handoff (R10).
  - (b) IN SCOPE for "incomplete streams" (REVIEW.md L50, acceptance 5). That item is about clients seeing a missing end line, not resume.
- **A8, Arrow vs JSON responses.** Snowflake may answer JSON, and then `GetArrowBatches` fails with `262001` (§3.6). The journey's planned SELECTs are not `SHOW` or `ls`, but the driver does not promise Arrow. Readings: treat 262001 as `upstream_failed`, or fall back to rows (doc.go L874-883).
- **A9, settlement and cost.** §6.4.1 L72 says "Rows, bytes and cost, from the engine's own record". `GetQueryStatus` gives `ProducedRows`, `ScanBytes`, `StartTime`, `EndTime`, and no cost (§3.14). §2.2.1.1 L72 points to query history by tag, which is SQL the guard would have to allow (registered objects only, Q-GUARD-1, QUESTIONS.md L112). AMBIGUOUS where cost comes from.
- **A10, the `database/sql` contract around `conn.Raw`.** The doc's Arrow pattern returns `rows` from inside `Raw` and uses it afterwards (doc.go L796-806). Reader's note: `Raw`'s contract keeps the driver connection only inside the callback. Holding the `*sql.Conn` (`db.Conn(ctx)`) until every batch is fetched, then closing it, keeps the pool from reusing the connection mid-stream. Alternatively use `SnowflakeDriver{}.OpenWithConfig` directly (driver.go L52). Neither source says.
- **A11, the decimal cast on the Arrow path.** §2.2.1.4 L128 calls the cast "mostly zero-copy ... `NUMBER(p,0)` to `int64`". With higher precision, a `NUMBER(p,0)` with p ≤ 18 can arrive as Int8, Int16 or Int32 (doc.go L837), and widening to Int64 is a copy. Q-SNOW-4 (QUESTIONS.md L107) has the SQL cast integers to `NUMBER(18,0)`. The physical width still varies per batch.
- **A12, goroutines from a dependency.** The driver starts goroutines with bare `go` (async.go L37; chunk_downloader.go L137, L167, L530; minicore.go L308). goleak (AGENTS.md L56) in tests that touch the driver must allow them, or such tests run only behind a build tag.
- **A13, cgo in `make check`** (§3.3): reading (a) release build only, or (b) every command with `-tags minicore_disabled`.
