# Pass 2 hardening: every finding, and what became of it

This is the ledger of the 2026-10-31/11-01 hardening. **Sources:**
- a ten-lens review of the built journey against the spec: 140 findings, each with a concrete failure scenario;
- a peer review: 10 findings, each confirmed by two independent refuters, one reproducing it in code and one checking the spec's authority.

**How they were fixed.** Ten lanes fixed them test-first, each lane owning its files. A failing test named for the finding came first, then the fix at its root. The usage limit stopped the lanes' second review pass. The integration after it:
- moved the data path onto `ports.DataSource`, and deleted the old warehouse port;
- split the production gateway into its own module, linking the cgo-free gosnowflake engine;
- fixed the review issues the limit had left open, rated P1 or worse, each with a test shown to fail without its fix.

`make check` and `make e2e` are green: every Go module under `-race`, the pure-Go release build, Python, Node, and the six acceptance points, each now asserting its outcome.

**Totals:** 126 fixed, 20 partly done, 1 not real, 3 open, out of 150.

## Still open, and who owns it

These need more than this pass had credit for. Each one is the review's or this plan's:
- **The conformance suite (R062, gaps/5).** It needs `sdk/go/conformance`, which serves the references' fixture gateway, scripted and recorded, plus the suite driver and runners for the CLI, Python and Node. The Go runner (the engine) already speaks §9.8.3. Owner: REVIEW.md step 4.
- **The step-3 mechanisms (R06–R08, R17; gaps/7).** Idempotency retention and fencing, confirmation and approval receipts, budget authority, durable operations, and separate start and execution deadlines. They are exercised on `conformance.costly`, `.change` and `.slow`. Owner: REVIEW.md step 3, when the first metered or changing capability arrives.
- **A hermetic RS256 issuer**, so the real `kit/jwt` verifier runs in every development and end-to-end test (CRITIC.md). Today the development gateway uses a token table.
- **Load and chaos** (PLAN.md §7, gaps/9): `tools/load` with SLOs as pass criteria, and fault injection for each blast-radius row.
- **The test-rule sweep (R121) and the requirement matrix (R122).**
- **Real systems (REVIEW.md step 5):** Snowflake, Entra OBO and group overage through Graph, and Azure stores. The gosnowflake engine is compiled and unit-tested, and runs nowhere live from this machine.
